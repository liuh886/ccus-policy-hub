# CCUS Policy Hub：产品定位与架构边界

> 决策日期：2026-10-30 · 状态：已确认的产品方向 · 适用范围：产品决策、架构评审与后续开发验收
>
> 本文件是**产品定位、模块职责和完成边界**的唯一权威；具体待办、依赖与实施进度只在 [ROADMAP.md](ROADMAP.md) 维护。未合并的 #101 / #103 / #104 是提案或实现候选，不自动代表主干已提供该能力。

## 1. 一句话定位

**CCUS Policy Hub 是面向研究人员和外部 AI Agent 的循证型 CCUS 政策、项目及治理研究数据基础设施（Evidence-grounded CCUS Policy Intelligence）。**

- **人读**：保留现有双语研究站、政策详情、设施情报、治理比较与学术报告。
- **机器读**：通过公开、结构化、可验证、可引用的静态数据接口提供 Agent-ready 数据。
- **共同基础**：两者读取同一份受治理的事实及分析投影；证据来源、时间口径和不确定性必须被保留。

**不建设专业问答 Agent。** 本项目只负责提供可信的数据和消费契约；问答、检索策略、提示词、工具调用编排、推理质量以及最终专业结论由下游使用者或其 Agent 自行承担。“能被 Agent 消费”与“本站能够替用户回答问题”不是同一个验收目标。

### 服务对象与产品承诺

首批人类用户是 CCUS 研究者、政策分析者和行业从业者；首批机器消费者是维护者自己的外部 Agent，之后可扩展到第三方脚本和 Agent。我们交付的是：**事实发现、可追溯引用、版本与时间语义、证据强度、可解释的比较口径、可验证的静态契约。** 不承诺全球法规穷尽、实时法律有效性判断、具体项目资格认定或法律/税务意见。

### 成功标准（不是 KPI 虚荣指标）

一个不依赖本站私有代码的外部消费者，能够从公开 manifest 发现资源、依据 JSON Schema 校验、按 ID 取得数据、定位来源、识别时间与翻译状态、区分地域背景关系与项目直接证据，并在缺失信息处得到明确的 `unknown/not_available` 语义。上述流程无需运行本站服务器或模型。

不采用“20 个问答准确率”“Agent 答案通过率”“生成最终法律结论”等指标验收本站。可使用真实研究问题作为**数据需求发现**，但只核验数据是否充分、正确可读、可引用，不评价或实现最终答复。

## 2. 架构职责与唯一权威

```text
官方法规 / 项目方 / 权威数据 / 已复核研究材料
                      │ 版本冻结、来源核验、人工审核
                      ▼
            SQLite SSOT（已接受结构化事实）
                      │ 只读、确定性投影；质量/关系/时间门禁
            ┌─────────┴──────────┐
            ▼                    ▼
     双语内容 / Astro 站点   public/data JSON + Schema
     学术报告独立同步       manifest + 任务型 context bundle
            │                    │
            ▼                    ▼
       人类研究用户         外部 Agent / 脚本
```

**数据的权威层级**：

1. 官方原文或直接来源是外部事实依据；其版本、内容摘要与获取时间必须可追溯。
2. `agent/ccus-ai-agent/db/ccus_master.sqlite` 是项目**已接受的结构化事实**的唯一可写权威。
3. `src/content/`、`public/data/`、Context Bundles、搜索索引和建成的 HTML 都是**生成产物**；不能直接手改来制造另一套事实。
4. 法规原文字节快照可以作为**带哈希的输入证据**存放于受版本管理的文件中；它不是第二个可写事实库。是否把原文、版本元数据或锚点入库，只在确有可验证的查询/维护需求时审查，避免同一原文同时在 Git 文件和 SQLite BLOB 中各维护一份。
5. ESG30 的论文原稿及 PDF 以其上游研究仓库为内容权威；本仓库负责一致的静态同步、页面阅读与部署，不负责重新创造一套论文事实库。

**模块边界**：

| 模块 | 拥有什么 | 不拥有什么 |
| --- | --- | --- |
| 数据维护层（SQLite + governed import） | 身份、事实、关系、评价口径、复核元数据 | 页面布局、Agent 提示词 |
| 证据层（官方来源/冻结版本/审核） | 来源元数据、文档版本、有效定位、审核状态 | 对项目法律资格的自动裁决 |
| 发布层（只读投影、JSON Schema） | 生成接口、引用 ID、数据字典、校验、完整性 | 数据事实修改、抓网、LLM 推理 |
| 人类前台（Astro） | 检索、浏览、展示分析口径与来源 | 私有数据标准、第二套计算/结论 |
| 外部 Agent | 自己的检索、提问、组织与推理 | 修改本站事实；本站不对其输出负责 |

先复用已有 `generate-public-data`、数据库只读查询、质量检查、Astro、Pagefind 和 JSON Schema。没有被真实消费者验证为必要的服务层、向量库、图谱、账户、权限、聊天 UI 都不加。**不写兼容层、不复制计算逻辑、不引入第二套存储权威。**

## 3. 开发工作包的“做到什么程度”

### A. 政策数据：可信覆盖，不追求法律大全

**应做**：维护当前核心政策身份、法域、类型、状态、来源、演进节点及已审核的分析维度；重点政策开展原文级深度复核；清晰标注发布/生效/审查时间的不同含义；有变更则提示重新核验。

**完成边界**：公开记录及双语投影与 SQLite 一致；每项已发布的关键事实可追溯至实际来源；未审核的条件仍为 draft/unknown；首批 45Q 证据能引用固定版本与具体位置。

**不做**：全部法域逐条全文收录；靠 URL 存在即认定法律内容已核验；为提高覆盖率自动晋级 draft；自动实时法律适用判断。

### B. 设施与政策关系：分离背景匹配和直接证据

**应做**：维持现有 1,110 条设施记录的身份、位置精度、状态、来源与可追溯更新；保留国家/地方匹配的原始类型与置信度；只在拥有直接、可审核项目证据时提升为直接证据关联。

**完成边界**：消费者可区分设施事实、坐标近似、地域背景政策和直接项目证据；导出与网站一致，缺失的直接证据不会自动推断；按优先队列修复高使用价值资料。

**不做**：推断项目必然受某政策约束、已获得补贴或具备 45Q 抵免资格；构造不可核查的源—汇连线；以收集全部设施新闻作为阶段目标。

### C. 治理比较：解释性研究工具，不生成伪精确裁决

**应做**：维护可复核的治理维度、聚合方法、数据口径及研究性比较；在国家对比中公开来源、分母与局限。

**完成边界**：同一输入重复生成一致结果；跨类型设施能力不误称为净捕集/封存能力；分位阈值与治理评分不被当作因果证明。

**不做**：将综合分数等同法律执行效果、项目可融资性或国家投资评级；未经方法学审核随意新增维度。

### D. Agent-ready 静态数据：交付契约，不交付问答系统

**应做**：复用 `/data/manifest.json`、`/data/*.json`、Schema；新增或扩展按稳定 ID 发现的、按需读取的 JSON/Markdown Context Bundles；明确记录身份、时间、来源、关联、审核状态、数据缺口、字段语言。保留 `llms.txt` 作为**发现文档**，不当作事实的独立来源。

**完成边界（全部可自动验收）**：

- manifest/index 能发现实际存在的资源；无隐藏私有 API 或手填生成路径。
- JSON 全量通过已发布 Schema；每个引用 ID 能解析到来源及其证据层级。
- 同输入重复生成**字节一致**；产物与已审核的 SQLite 数据保持一致。
- en/zh 缺译标注原文语言，不伪造中文；draft、未复核、历史版本与未知适用性不得静默升级。
- 外部消费者仅用公开资源就能完成“发现 → 校验 → 读取 → 引用/判断缺口”的数据消费 smoke test。错误 ID/语言产生明确错误，不返回貌似成功的空数据。
- 变更资源字段时同步维护 schema、生成器、文档与自动化测试；**不为了假定的旧客户端留兼容字段**。

**不做**：聊天页面、站内问答端点、提示词工程平台、LLM 服务、RAG/向量检索平台、回答准确率 benchmark、Agent 工作流编排、税务资格决策器；没有证据证明静态接口不足时不开发 MCP。

### E. 法规证据：一个可用纵向样例，拒绝预防性大建模

**应做**：先用美国 45Q 完成一个公开文档版本和至少一处原文锚点的可审核、可失效验证闭环；版本哈希、来源 URL、获取/发布/覆盖日期、定位器、审核状态各司其职；对历史快照明确说明**不能证明当前法规状态**。

**完成边界**：经过人工复核的一条法规证据可由 Agent-ready 数据引用；篡改、文档换版、抽取规则变化时，相关定位与审核状态被检查阻止继续当作有效证据；证据不足时只导出不足，不自动推断。

**数据库决策门槛**：#104 的 `source_documents`、`source_document_versions`、`source_document_anchors` 是**待审提案**，不是已获批准的最终架构。先检验现有政策表 + 版本化原文文件/清单是否能完成上述闭环；只有在出现多文档、多版本、跨政策查询或人工复核无法稳定管理的**实际需求**时，才批准最小必要 schema，且先审查原文字节的唯一存放位置，禁止无意义的双份正文存储。已申请的 schema 变更仍须按维护规则独立批准。

**不做**：全面 45Q 法条自动解释、自动计算税收抵免、批量条件卡、历史时点状态推断、自动判定单个项目满足法定条件。条件卡只在能够增加**数据可用性**时作为带来源的结构化记录提供；绝不承担判定引擎职责。

### F. ESG30 数字出版：保留论文体验，隔离维护职责

**应做**：跟随上游权威版本自动生成并发布 HTML/PDF；检查同步、结构完整性、引用与部署一致性；保持偏论文阅读的体验。

**完成边界**：上游内容更新后有可验证的同步和 Pages 发布链条；站内指向的版本与实际交付一致。

**不做**：在 Policy Hub 手工编辑研究正文、重建论文 CMS，或为增加平台功能而改变学术阅读性质。

### G. 工程治理：可靠且低摩擦，不扩大无关复杂度

**应做**：在数据库/模式变更时保留强审计；文档与 UI 变更使用与影响范围匹配的 CI；验证必须只读；区分 CI 成功与实际发布一致性；维护单一 ROADMAP 和明确的 PR 依赖关系。

**完成边界**：改动层对应的质量门禁通过、主分支可生成可部署、Pages 产物可检验、无错误的陈旧文档声明；维护说明指向同一份事实来源。

**不做**：重复运行的整套构建和审计、为了未来可能用到而配置复杂发布基础设施、以测试数量代替产物正确性。

## 4. 按依赖落地，而不是按功能数量落地

| 阶段 | 入口/依赖 | 本阶段交付的最小纵向结果 | 停止扩展的条件 |
| --- | --- | --- | --- |
| P0：清理基线 | 主干与 #101–#104 的当前状态 | 合并已审查的 #102 数据/维护改进；修订 #101 与本定位冲突的问答验收；#103 按依赖进入主干；#104 继续 draft 审核 | 主 ROADMAP、主干能力声明和实际发布一致；不以“PR 已有实现”冒充上线 |
| P1：Agent-ready 契约 | P0，复用已有导出 | 45Q 现有政策族 bundle 供真实外部消费者按 manifest → schema → data → reference 使用 | 契约/引用/时间/双语/缺口的正反用例全过；**不产生 Agent 回答** |
| P2：单条法规证据闭环 | P1，#104 可用候选 | 一份固定版本的官方原文 + 一处已复核锚点可按 ID 被读取，版本变化可使其失效 | 审核者可追踪原文、版本和证据状态；无完整法律解答承诺 |
| P3：复用示范 | P2 | 选择最多 2–3 项跨法域重要政策验证同一证据契约，无新产品入口 | 不改核心契约即可新增法域；如必须改动，则收敛领域模型而非叠加例外 |
| P4：运营与体验收敛 | P1–P3 反馈 | 清理失效任务、按使用需求补高价值数据、优化现有政策/项目/质量入口 | 不加新的核心模块；以数据可靠性、维护成本、消费成功率为准 |

每个阶段原则上一个聚焦 PR；数据事实修正和 UI 调整不得混成不可审核的巨型改动。先在维护者的外部 Agent 中完成消费 smoke test，但**不得因为消费方是 Agent，就把问答/推理代码迁回本站**。

- **#101（Draft）**：保留可实现的 bundle、版本、来源、缺口与只读契约；将 `us_45q_policy_qa` 的“问答作为本站验收任务”改成 `us_45q_context_consumption`。删除以问答质量、项目资格回答、问题集正确率验收本站的表述，改为数据消费者契约测试。必须在合并前消除与本文冲突的 S3/S4 范围描述；不得建立第二套路线图。
- **#102（Open）**：保留数据质量、来源复核、证据层级、双语与前端可靠性改进；优先完成审核与合并。其“直接证据仍为零”不能通过生成假设性关联消除。
- **#103（Open）**：保留 JSON/Markdown bundle、manifest、schema、CLI、确定性检查与只读构建，作为 Agent-ready 的最小交付；把与完整问答能力有关的未来声明限制为数据覆盖缺口。不需要添加 Agent runtime。
- **#104（Draft）**：保留候选原文、抽取/哈希/锚点测试及只读迁移预览；真实数据库 schema 迁移和条件卡晋级继续暂停，先按 §3E 证明最小闭环、解释存储选择与时效覆盖。不能把 2024 历史法典快照当作现行 45Q。

## 6. 变更原则与验收证据

- 所有新增数据功能先描述 **用户需要消费的字段及语义**，再给出最少存储和生成路径，最后才允许新表或新服务。
- 禁止把“未查到”当“不适用”；禁止把“当前快照”当“历史时点”；禁止将 country/subnational 地域匹配提升为 direct evidence。
- 每个实现 PR 应在说明中列出：权威输入、具体生成产物、schema/字段变化、边界负例、运行命令、CI 结果和不在范围的事项。
- 验收数据接口时必须同时检查**正确事实、正确缺失、正确引用、正确失效、确定性生成**；不采用语言模型生成的一段漂亮答案作为通过依据。
- 工程优先级：已运行的最小端到端数据消费 → 稳定契约 → 选定法规来源增强 → 小规模复用 → 根据真实维护成本改善。任何阶段都不为未验证的未来复杂度拆掉已经能工作的路径。

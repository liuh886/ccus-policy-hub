# 知识萃取的质量、工程分工与成本论证

状态：2026-10-31 / RFC #112 Round 4，**proposed**。目录接入继续执行；知识萃取的输出合同与模型路线尚未批准。本记录回答“怎样才算好的知识萃取、怎样实现最合理”，不另建活动队列，不把原文转换、模型输出或引文定位冒充已审核知识。

## 先定义交付对象与质量

目录负责“有什么资料、哪个版本、怎样访问”；文本解析负责“原文写了什么、在哪里”；知识萃取才负责“哪些命题被这些原文支持，条件与范围是什么”。JSON 是这些对象的载体，格式正确本身不证明知识正确。

好的萃取结果应同时满足：

| 维度           | 要回答的问题                             | 错误例子或检查                                         |
| -------------- | ---------------------------------------- | ------------------------------------------------------ |
| 身份与版次     | 是否真是这份文书、这个版本？             | 上传目录中的年份不能当法律版次；原文哈希必须匹配       |
| 支持性         | 支持原句是否足以推出这个命题？           | 原文“满足 A 且 B”不能抽成“满足 A 即可”                 |
| 原子性与完整性 | 是否拆到可核验，同时保留必要限定？       | 拆句不能丢掉否定、例外、期限、定义和跨条引用           |
| 数值与口径     | 数字、单位、分母、统计期、脚注是否一致？ | 报告中的规划容量不能变成实际运行容量                   |
| 可定位性       | 原句能否在冻结字节的正确位置复现？       | PDF 物理页与印刷页分别记录；HTML 定位绑定规范化版本    |
| 证据类别与时间 | 是法规陈述、报告观点还是推论？           | 2024 历史法条不能自动成为现行法；报告不承担法规效力    |
| 不确定性       | 缺失、冲突、未审、许可限制是否可见？     | OCR 错误或缺失字段不能被零值、模型补全或 verified 掩盖 |

[FActScore](https://aclanthology.org/2023.emnlp-main.741/) 用有来源支持的原子事实比例衡量事实精度。对本项目还必须检查重要限定的覆盖，因为“只抽简单正确句”会获得高精度，却可能遗漏决定意义的例外。[ALCE](https://aclanthology.org/2023.emnlp-main.398/) 区分文本正确性与引用质量，支持我们把“原句可找到”和“原句足以支持命题”作为两种检查。这里借鉴评价思想，不引入站内问答或最终回答准确率评测。

## 推荐分工：确定性程序、模型、审核各做什么

```text
冻结原文 + 版本/访问边界
        ↓ 确定性程序
结构化正文、章节、页/表图、原文定位
        ↓ 需要语义提炼时才调用模型
带限定语和证据集合的候选命题
        ↓ 程序校验 + 支持性核对 + 必要人工审核
受审知识资产 / 明确缺口
        ↓ 同一来源与审核输入的确定性投影
静态目录、证据记录和外部消费者
```

- **程序**：核验字节、识别文件类型、解析结构、切分文档、构造稳定定位、校验 schema、数值格式、引用是否存在，以及生成发布文件。目录生成器只处理这些已登记输入，不自己猜知识。
- **模型**：在给定章节/页及必要上下文中识别候选命题、限定语、术语关系和可能的支持证据。每个输出必须引用提供的 source/section/page ID；允许输出“不足以判断”。模型不能签署 human review，也不能仅凭输出 JSON 就更新 SQLite 已接受事实。
- **核对与审核**：检查命题是否被完整支持、是否需要定义/相邻条款/表头脚注、是否混用版本。程序找不到引文可以直接拒绝；程序找到引文仍不足以自动批准支持关系。模型自评或多个模型一致只能辅助筛查。

例如，资料“原始法案第 2 条的标题”适合确定性提取；“这些条款共同构成什么义务”需要限定语和交叉引用的语义核对。报告的图题可提取为定位，图中的箭头、表格单位与列间关系需要布局/视觉证据，不能从一串线性文字自动补全。

## 三条工程路线的取舍

| 路线                                                | 优点                                     | 主要缺陷                                             | 本项目建议                           |
| --------------------------------------------------- | ---------------------------------------- | ---------------------------------------------------- | ------------------------------------ |
| 整份 PDF 直接交给大模型生成知识 JSON                | 原型快，能尝试视觉内容                   | 重复成本高；定位、换版失效、长文条件覆盖难以独立验证 | 用于受控小样本对照，不作为默认流水线 |
| 确定性解析 + 结构分块 + 选择性模型提炼 + 支持性核对 | 可缓存、可追溯，解析与语义错误可分别定位 | 需要维护结构与定位，复杂版面要升级解析路径           | **条件性推荐的主路线**               |
| 先统一成大型本体/知识图谱或完整条件规则库           | 可支持复杂关系查询                       | 初期语义承诺与审核成本大，容易在实际需求前制造结构   | 尚无消费需求和实证，不先建设         |

默认先复用已有 HTML 解析与 Poppler 数字 PDF 提取。出现多栏、表格、图形关系或扫描页时，才对相关页试验布局解析或 OCR，并比较相同标注单元。[Docling](https://arxiv.org/abs/2501.17887) 是结构化文档转换的候选工具；本轮没有安装/运行它，也不声称它在 CCUS 样本上胜过现有解析器。工具选型应由实际故障与测量决定。

## 怎样提高效率而不牺牲证据

1. **按原文字节哈希复用**：解析缓存键含 raw SHA、解析器/规范化版本；模型候选再加模型、提示词和输出 schema 版本。目录重新生成不调用模型。
2. **按结构处理**：保留章/节/段、定义、表头、脚注和父级上下文；限定符有关联时一起送入提炼。使用 token 上限控制预算，但不以任意固定长度替代文书结构。
3. **按需升级**：目录和标题识别先走确定性路径；只把需要语义提炼的片段送给模型；仅对复杂版面/扫描页使用布局模型或视觉 OCR。
4. **候选先校验再审核**：先过滤不存在的引用、错版、丢单位和重复项，把人工时间用于支持性、例外与冲突。不要把复核全部交给同一个生成模型自评。
5. **增量失效明确**：版本、解析器、提示词变化可使候选失效；即使某页哈希未变，新的定义或修订也可能改变意义，不能自动继承“现行法已审”。
6. **保留适合消费的中间层**：Git 管可公开的版本/定位/审核输入，SQLite 管已接受结构化事实，私有原件留在归档。静态输出只是这些输入的投影。

## 在承诺“最好”之前，还缺什么实证

建议在三种来源上建立一个小型、经人工标注的同题样本，覆盖普通陈述、数值单位、条件/例外、跨条定义、图表、历史版本及未知访问权限。比较“整份模型直读”与“解析后选择性提炼”，固定模型版本、输入范围与输出预算。

分别记录：支持性精度、重要限定覆盖、数值/单位一致性、定位成功率、错误升级数、每个可接受知识项的复核分钟数、处理时间、实际 token/调用成本和缓存命中。原文/版次/定位错误、未审内容自动升级、权限泄露应作为阻断项；平均分不能冲掉关键错误。小样本只用于暴露故障，不能宣称总体准确率。

当前没有经过人工标注的语义 gold set，也没有真实模型费用/延迟对照。因此本轮能确认的是三份真实目录与定位消费链路、解析成本和现有缺口；不能确认语义萃取最优模型、Docling 优越性或某个知识输出 schema 已被采纳。下一步的工程路线有依据，但质量结论仍需上述对照。
